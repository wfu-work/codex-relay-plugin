# 官方桌面与 Relay 插件共享后端：第一阶段验证

日期：2026-09-10。结论：**当前安装版本的核心接入验证通过，可以进入共享连接改造；完整的双端交互一致性尚未完成。**

这次使用真正的官方桌面应用和插件现有 `AppServerClient`，没有用两个自制客户端代替桌面验证。正式桌面、Relay 配置及业务任务未迁移。

## 找到的接入方式

当前安装包包含以下入口，来自只读代码检查：

1. `CODEX_APP_SERVER_WS_URL`：桌面直接连接指定 WebSocket App Server。本次实际采用并验证。
2. `CODEX_ELECTRON_USER_DATA_PATH`：为测试桌面隔离 Electron 数据目录；配合独立 `CODEX_HOME`，无需重启正式实例。
3. `CODEX_APP_SERVER_USE_LOCAL_DAEMON=1`：存在本地 daemon 连接逻辑，但有平台、配置覆盖项等条件。本次没有实测该分支，不作为已经可用的生产方案。
4. 桌面 SSH 分支使用 `app-server --listen unix://` 和 `app-server proxy`。本次未配置 SSH 主机，也未验证该路线。

这些内部开关存在于当前安装版本，不代表公开且稳定的第三方接入承诺。测试没有修改官方应用安装包。

实际链路：

```text
官方桌面（独立测试实例） → 本地透明 WebSocket 记录器 ┐
                                                     ├→ 同一个 App Server，PID 48130
现有 AppServerClient → 测试用 stdio/WebSocket 适配器 ┘
```

适配器只转换 JSONL 与 WebSocket 帧，不调用第二个 Codex 执行进程，也不模拟模型回复。记录器只保存方法、任务/轮次标识和事件数量，不记录认证响应。

## 对后续方案的影响

### 可以确认的部分

当前版本无需修改官方应用二进制，就能让桌面和插件共享一个执行实例。同一任务的写入冲突可以通过这条路线消除。可以着手第二阶段的连接和生命周期改造。

正式实现应使用独立的传输适配层。插件退出只断开连接，共享连接失败时不得自动启动另一个 writer。服务状态、事件订阅和快照恢复要基于同一个执行实例。

### 必须保留的限制

- **不能把共享 App Server 等同于完整共享桌面队列。** 安装包显式把 `thread/queue/changed` 加入通知排除列表，也没有发现桌面调用该队列 API 的路径。即使后端队列能正常执行，也需要继续研究桌面现有的排队入口，或明确产品行为的差异。仅在插件里新增队列无法使桌面队列 UI 自动同步。
- **开始回执与实际执行之间存在短暂窗口。** 发送状态应区分已接受和正在执行。停止请求需要保存用户意图并核对实际轮次，不能遇到 `no active turn` 就误报已停止，也不能对后续轮次无条件重试。
- **审批与宿主能力需要专门验证。** 当前插件只处理部分审批请求，其他客户端请求会返回不支持。共享模式下，必须验证请求归属、重复响应、问题回答，以及桌面专属工具的配置注入。
- **入口存在版本依赖。** WebSocket 地址开关在当前版本实测有效；本地 daemon / SSH 路线只得到静态证据。上线前应锁定兼容版本、检测能力，并提供回滚启动方式。
- 本次仅进行了短时、本机验证，没有覆盖网络中断、服务崩溃、电脑休眠、长任务、多项目权限及升级回归。

## 复现与证据

后续复现应继续使用独立桌面配置目录、独立测试任务和本地监听。先启动测试 App Server，再用 `CODEX_APP_SERVER_WS_URL` 启动官方桌面；让现有插件客户端通过纯传输适配器连接同一个地址。手动从桌面发送测试消息，以真实客户端请求和用户确认共同验收，不能只验证两个脚本互通。
