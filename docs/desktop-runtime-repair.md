# 共享服务的桌面工具签名链

2026-09-11：当前 macOS Codex 会验证桌面工具进程及其父、祖父进程的
签名身份。原先服务使用 `process.execPath`（本机为系统 Node），即使
工具和 App Server 都来自官方安装，仍出现
`dynamic_app_tools_peer_rejected reason=untrusted-code-signing-identity`。

在相同桌面 Socket 上，使用官方 Node 启动隔离后端后，真实 `tools/list`
在约 0.5 秒内返回 27 个工具。该实验未发送模型请求，也未修改桌面签名或关闭授权。

修复方式：

- 共享 LaunchAgent 和新准备包使用桌面自带的签名 Node；服务启动前验证签名及实际运行路径。
- 固定 MCP 的官方运行时和桌面 Socket，避免 `env_vars` 覆盖它们。
- 对已运行的系统 Node 服务直接报告“共享服务运行时待修复”；不会误报为签名文件损坏或等待整个 MCP 目录超时。
- 工具目录查询只请求 `toolsAndAuthOnly`，处理分页并限制总等待时间。
- 控制台修复任务独立于桌面运行，等待退出桌面和全部共享任务空闲，再备份并更新当前注册服务的启动文件，重启并重新打开桌面。
- 已启用的共享安装重启由实例锁、进程归属和专用 Socket 保护；初次迁移仍检查旧后端冲突。
- 重启失败恢复旧启动文件；历史、Relay/API 配置、项目权限不在修复写入范围。

修复等待最长 15 分钟；等待期间不要从 Flutter 发起新任务。正在运行、等待审批、等待用户回复或未知状态的任务都会阻止重启。代码更新本身不代表旧服务已切换，必须查看重启后的进程和真实目录检查结果。
